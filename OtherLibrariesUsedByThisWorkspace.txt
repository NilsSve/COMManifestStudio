Libraries used by this workspace
================================

COMManifestStudio uses five libraries:

    Filesystem, DUF, DFAbout, RDCToolsLib, vwin32fh

This is a DataFlex 26 workspace, and they do not all arrive the same way.

COMManifestStudio.sws declares two dependencies. Filesystem is a local one,
read from Libraries\. DUF is a git one, pinned by commit. DataFlex 26 unions a
dependency's own dependencies into the workspace, so DFAbout, RDCToolsLib and
vwin32fh come along with DUF without being named here, even though this
workspace's own source uses all three directly (cRDC* classes, vWin32fh.pkg and
the About dialog).

The Studio's package handler unpacks the git ones into DfPkg\ and records the
exact commit of each in COMManifestStudio.sws.lock, which IS committed - it is
what makes a clone build the same library versions as the machine it came from.
DfPkg\ itself is not committed, any more than Libraries\ is.

setup.bat provides Libraries\ - see README.md.


One copy on the search path, and only one
-----------------------------------------

An older arrangement declared DFAbout, RDCToolsLib and vwin32fh only inside
DUF, and reached them through Libraries\DUF\Libraries\ . The reasoning was
that declaring them in two places would confuse git. That was sound for
submodules, and it caused a worse problem: every consumer ended up with its own
physical copy of each library on disk, and the Studio navigates by disk.
Go-to-Definition would open whichever copy it found first, so a library fix
could be made in one copy while the build compiled another - silently
diverging, and needing manual propagation afterwards.

That is the reason setup.bat clones Filesystem and nothing else. The other four
live in DfPkg\, the compiler reads them there, and a second copy under
Libraries\ would only be a place for a fix to get lost. On a machine with the
shared RDC library pool next door, Libraries\ is a junction to it, so even
Filesystem is one editable copy shared by every workspace on the machine.
