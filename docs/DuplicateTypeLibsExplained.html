  1. Background

Duplicate type libraries

Windows needs every COM class and every ProgID in a manifest to be unambiguous. When two fragment files declare the same thing, the manifest cannot be used, so COM Manifest Studio checks for it before it writes the manifest, and names the files.

Two builds of one component

The most common case today is the 32-bit and the 64-bit file of the same component - Codejock's x86 and x64 files declare the same COM classes. A program can use only one of them: the one for its platform. Remove the other from the list. See 64-bit programs.

Different versions of a component

Duplicates also come from different files that implement different versions of the same component. As a component changes, new files are released, sometimes with the same name and sometimes with another. Choose the version your program is built with.

Duplicate ProgIDs in one file

A file that implements several versions of a control can have several classes that use the same version-independent ProgID. The registry allows that, so it is common, but Windows' side-by-side loading requires that a ProgID leads to exactly one class, and the other way round. For example, a component may register:

HKEY_CLASSES_ROOT\CLSID

    {BAD00001-...}   ProgID ProgidSample.ProgIDSample.1   VersionIndependentProgID ProgidSample.ProgIDSample

    {BAD00002-...}   ProgID ProgidSample.ProgIDSample.2   VersionIndependentProgID ProgidSample.ProgIDSample

    {BAD00003-...}   ProgID ProgidSample.ProgIDSample.3   VersionIndependentProgID ProgidSample.ProgIDSample

HKEY_CLASSES_ROOT

    ProgidSample.ProgIDSample   CLSID {BAD00003-...}   CurVer ProgidSample.ProgIDSample.2

The three classes share one version-independent ProgID, and that ProgID even points to a different class through its CLSID than through CurVer. In a case like this, the fragment file must keep only one of the declarations - the one the program uses.
